# Архитектура

Документ для человека и для защиты: что где лежит, почему так, и чем это проверяется.
Правила для агента — в `AGENTS.md`. Что уже разъехалось между ветками и требует починки —
`docs/DECISIONS.md`, раздел «Реконсиляция веток».

## Почему не «стандартный layout»

`golang-standards/project-layout` — не стандарт. Это репозиторий одного человека
с 2017 года; Russ Cox, техлид Go, публично написал, что это не стандартная раскладка,
что подавляющее большинство Go-пакетов не кладёт импортируемый код в `pkg/`, и что
Go-репозитории обычно проще. Официальная рекомендация — начинать просто и добавлять
структуру, когда появляется боль. Единственное правило, которое реально проверяет
компилятор: пакеты в `internal/` нельзя импортировать снаружи модуля.

Мы всё же используем `backend/pkg/` — но не как в том репозитории (свалка «переиспользуемого
на будущее»), а буквально для одной вещи: общей инфраструктуры (`pkg/postgres` сегодня,
`pkg/ws`/`pkg/ingest` — когда понадобятся), которую уже импортируют и `feat/auth`, и
`feat/pet-service`. Переименовывать этот путь под двумя ветками, которые от него уже зависят,
дороже, чем нарушить чужую условность.

## Раскладка (целевая — см. DECISIONS.md про текущий разъезд веток)

```
backend/
├── cmd/main.go                   точка входа: только wiring, никакой логики
├── internal/
│   ├── pet/                      ─┐
│   ├── tasks/                     │ один пакет на тег OpenAPI
│   ├── streak/                    │ handler.go / service.go / repo.go
│   ├── rewards/                   │
│   └── social/                   ─┘
├── pkg/                          postgres, позже ws, ingest — общий нижний слой
├── migrations/                   goose
└── db/query/                     SQL для sqlc
```

`cmd/main.go`, а не `cmd/api/main.go` — так фактически лежит на всех трёх ветках
(`main`, `feat/auth`, `feat/pet-service`), переносить без причины не стали.

**Почему пакет на тег OpenAPI.** Границы кода совпадают с границами контракта. Когда
меняется тег в спеке, понятно, какой пакет трогать; когда меняется пакет, понятно, какой
кусок спеки поедет. Один синхрон вместо двух. Для команды из четырёх человек это ещё и
разделение зон: пакет — единица владения, и два человека реже правят один файл.

**Почему `pkg/` отдельно.** Postgres-пул (и то, что к нему добавится: WS-хаб, ингест
событий) нужен всем фичам. Если положить их в фичевый пакет, фичи начнут импортировать
друг друга ради инфраструктуры, и слоёв не станет.

## Слои и что кому можно

| Слой | Файл | Можно | Нельзя |
|---|---|---|---|
| Транспорт | `handler.go` | Gin, сгенерированные типы, свой `service.go` | БД напрямую, sqlc, pgx |
| Домен | `service.go` | чистые функции, свой `repo.go` через интерфейс | `net/http`, Gin, sqlc, pgx, `time.Now()` |
| Данные | `repo.go` | sqlc, pgx | HTTP, доменные решения |
| Платформа | `pkg/*` | стандартная библиотека, драйверы | импорт любого пакета из `internal/` |

**Это проверяется, а не просится.** В `.golangci.yaml`:

- `depguard` → правила `service-layer`, `handler-layer`, `platform-layer`
- `forbidigo` → `time.Now()` вне `pkg/` и `cmd/`
- `exhaustive` → забытый `case` в switch по статусным enum'ам

Нарушение слоя — красный линтер в CI, а не находка на ревью в последний день. Правила пока
матчат только целевой layout (`internal/<tag>/{handler,service,repo}.go`) — на существующем
коде `feat/auth`/`feat/pet-service` они пока ничего не находят, потому что там другая
раскладка. Это ожидаемо до реконсиляции, не повод её откладывать.

## Поток данных

**Начисление.**

```
POST /v1/events → ingest → event_inbox (idempotency key)
                         → energy_ledger (+ source: gamified|organic)
                         → pet state (XP, level) → WS push
```

`source` проставляется в `event_inbox` и должен дойти до `energy_ledger` без потерь —
на этом держится анти-абьюз и вся аналитика «геймификация против органики». Проверяется
интеграционным тестом против настоящего Postgres, не ревью.

**Выдача награды (критический путь).**

```
POST /v1/rewards/{id}/claim
  → BEGIN
  → SELECT ... FOR UPDATE по пользователю
  → проверка eligibility (уровень / стрик / достижение)
  → INSERT INTO reward_grants (UNIQUE (user_id, reward_id))
  → COMMIT
```

Гонка здесь означает задвоенный грант. Транзакция плюс UNIQUE-constraint — не
рекомендация, а то, что делает выдачу однократной. Тест на гонку с `-race` против
Postgres в testcontainers — обязательный, и это лучший момент демо.

`REWARD_NOT_ELIGIBLE` → **409**, не 403: это состояние, а не права доступа.

## Инварианты

1. Прогресс начисляется только по реальному событию Авито *(открытый вопрос — см. DECISIONS.md; уже де-факто нарушен хардкодом в `feat/pet-service`)*.
2. Награда привязана к пользователю; никакой пересылаемой строки-кода.
3. `source` не теряется на пути `event_inbox` → `energy_ledger`.
4. Выдача награды однократна при конкурентных claim'ах.
5. Время в домене — параметр, не `time.Now()` внутри.
6. Прогресс пользователя не обнуляется миграцией.

Инвариант 5 — не стиль, а то, что делает 1–4 тестируемыми: `decay(state, from, to)`
проверяется обычным табличным тестом, `decay(state)` — ничем. Там, где время параметром
не сделать (WS-хартбиты, таймауты реконнекта, истечение грантов), тест идёт внутри
`synctest.Test` — фейковые часы, тест на 30 секунд исполняется за микросекунды и не флакает.

## Redis — сознательно не используем (см. DECISIONS.md → «Открытое»)

Не добавлен. Postgres — единственный источник истины и единственный стейт-сервис на
масштабе хакатона. Если появится обоснованная причина (реальная нагрузка на лидерборд,
измеренная, не предполагаемая) — это отдельное решение с записью в DECISIONS.md, не
дефолт, унаследованный от черновика.

## Демо и время

У приложения ядро — время: распад состояния, суточные границы стрика, истечение грантов.
Жюри смотрит десять минут и физически не может увидеть, как проходит время.

Поэтому нужен служебный эндпоинт сдвига часов (только при `APP_ENV=demo`) — почти
бесплатен именно потому, что время в домене параметр: сдвиг часов не требует ничего,
кроме передачи другого `now`. Плюс `make seed` — пользователь в середине стрика, один
у порога уровня, один с готовой к получению наградой, заполненный лидерборд. Оба пункта
из «не сделано» в `docs/DECISIONS.md`.
